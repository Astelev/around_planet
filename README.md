# around_planet

Minecraft 1.21.1 / NeoForge 21.1.256, Java 21. Имя и mod ID: `around_planet`.

**0.9.3-diagnostic развивает независимый движок around_planet.** Immersive Portals /
Immersive Aeronautics больше не являются зависимостями. Перед проверкой уберите
портальный fork из `mods` / `run/mods` и обновите Gradle-проект; физический
Aeronautics и Sable — отдельные моды. Ничего патчить в сторонних JAR не нужно.
Разбор портального движка используется как архитектурный ориентир, его код
в новый рендер не копировался. [Новый этап](docs/independent-renderer.md).
Настройки портального backend 0.4.x больше не используются; `enabled` и
`boundaryX` сохраняют смысл. Для нашей подгрузки снова используются
`activationDistance` и `destinationRadius` из примера ниже.


**0.10.2:** исправлен перенос пассажиров в нативных сиденьях Sable: служебные координаты сиденья остаются неизменными, игрок переносится вместе с конструкцией. [Причина и проверки](docs/seated-transfer-0102.md).

## Экспериментальный переход запад ↔ восток

Серверный перенос обычных сущностей и игрока между краями Overworld.
Периодическая координата X лежит в `[-boundaryX, boundaryX)`.
Например, при `boundaryX = 256`: `256.75 → -255.25`, `-256.125 → 255.875`.
Высота, Z, направление взгляда и скорость сохраняются при готовом переходе.
Север/юг не изменяются. С 0.9.0 новая шумовая генерация сглаживается в полосе у западного и восточного шва.

**По умолчанию выключено.** Установите мод на сервер и клиент и включите в новом
тестовом мире: `<world>/serverconfig/around_planet-server.toml`:

```toml
[eastWest]
enabled = true
boundaryX = 65536
activationDistance = 128
destinationRadius = 2
retainTransitionMeshes = true
transitionMeshMaxMiB = 128
transitionMeshMaxSections = 1536
snapshotRefreshTicks = 10
snapshotChunksPerTick = 2
dhSeamRendering = true
dhPreviewDistanceBlocks = 512
shipSeamSupport = true
shipSeamBandChunks = 8
shipSeamTransfers = true
guardMarginBlocks = 1024
terrainSeamBlending = true
terrainBlendWidthBlocks = 256
seamDiagnostics = true
```

После изменения настроек перезапустите мир. `boundaryX` задаёт координаты обоих краёв: по умолчанию это **−65536 и +65536**,
а полный оборот равен 131072 блокам. Значение должно быть кратно 16, от 128
до 29500000; центр по X — ноль. Для небольшого теста можно выбрать 256.
Старый ключ `widthBlocks` заменён на `boundaryX`: прежняя настройка задавала
полную ширину и ошибочно трактовалась как координата края. При обновлении
укажите нужную координату в новом ключе; по умолчанию это 65536.
Зона активации ограничена четвертью полной ширины мира. При быстром движении она
автоматически расширяется до двух секунд пути, максимум до 1024 блоков. Настраиваемый радиус назначения — 1–4 чанка. Для игрока и транспорта с игроком
билеты покрывают ещё одно кольцо, необходимое полосе визуальных снимков.
Обычные сущности используют меньшую область и начинают подгрузку ближе к краю.

В зоне активации временные билеты заранее загружают противоположный край.
Игрок проверяется сразу после обработки принятого vanilla пакета движения,
без дополнительного ожидания следующего серверного тика. При неготовом или
занятом назначении ожидание остаётся необходимым.
Не более 16 областей назначения одновременно. Запрос игрока может вытеснить
область обычной сущности, чтобы мобы/предметы не блокировали переход навсегда.
Билеты истекают через 100 тиков
после прекращения обновления. Код перехода не ожидает генерацию синхронно.
Если место назначения ещё не загружено, объект удерживается у исходного края.
При таком ожидании отступ за край может быть потерян. Коллизии блоков у шва
проверяются по видимому периодическому рельефу обычным алгоритмом движения.

Штатный world border ограничен только по X, по умолчанию на 1024 блока снаружи линии перехода:
этот запас позволяет пересечь линию до включения коллизии border. Границы по Z,
сохранённые центр и размер vanilla border не меняются. Линия перехода находится
на точном `boundaryX`, а не на внешней стене. `guardMarginBlocks` (16–16384) —
только страховочный запас; он должен превышать максимальный свес корпуса с
учётом роста игрока и дальности взаимодействия. Красное затемнение экрана от проходного шва отключено.
Предупреждение от более узкого обычного border сохраняется. Более узкий существующий
border сохраняет приоритет — его надо расширить для доступа к линии перехода.

## Изображение противоположного края

При включённом переходе реальные загруженные чанки другой стороны автоматически
отображаются за швом. Копии используют штатную сборку секций Minecraft: модели
блоков, воду, прозрачные слои, свет и цвета биомов. Синяя стена border на шве
скрыта; её страховочная коллизия остаётся прежней.

Поддержаны штатный рендер и Sodium; игровой прогон выполнен с Sodium 0.8.13
для Minecraft 1.21.1 / NeoForge, совместно с DH 3.3.3, Cruising Speed и Sable 2.0.6.
Адаптер Embeddium предусмотрен, но пока не проверен в игре. Iris/Oculus и
шейдерпаки отдельно не проверялись.

Изображение ограничено уже подготовленной областью `destinationRadius` (по
умолчанию несколько чанков). Это визуальные копии данных, из которых клиент собирает геометрию, а не видеопоток.
`snapshotRefreshTicks` задаёт минимальный интервал проверки изменений (10 тиков,
0,5 секунды при 20 TPS). Очередь добавляет задержку; сначала проверяются наиболее
давно проверенные колонки, поэтому частые проверки не вытесняют дальние.
`snapshotChunksPerTick` ограничивает число проверок и сериализаций за тик
на игрока (по умолчанию 2, разрешено 1–8); неизменившиеся снимки не пересылаются.
Клиентский
кэш — 192 колонками. Слишком большой снимок (свыше 900 КБ) пропускается с записью
в серверный лог. Для отображения обновите мод на сервере **и** клиенте.

Обычные билеты дальности обзора и отправка настоящей территории за границей
отключены. Служебные соседние чанки для генерации, освещения и физического запаса
не блокируются: жёсткий запрет всех соседей мог бы остановить генерацию края.
Существующие сохранённые чанки за границей не удаляются.

С DH 3.3.3 отключаются запросы генерации целиком за границей и показ внешних LOD.
Секции LOD, пересекающие шов, консервативно скрываются целиком. Их отображение с
противоположной стороны ещё не реализовано. Биомная поверхность Cruising Speed
также маскируется за швом. Визуальные копии не отправляют `ChunkEvent.Load` и не
попадают в базу DH или сохранения мира.

Устройство и ограничения: [docs/seam-rendering.md](docs/seam-rendering.md).

В той же полосе показываются отдельные изображения обычных сущностей: мобов,
игроков, предметов, стоек для брони и транспорта с пассажирами. Состояние
обновляется каждые 4 серверных тика, движение интерполируется. Изображения не
входят в игровой список сущностей: их нельзя ударить, подобрать или столкнуть.
Серверные сущности остаются в единственном экземпляре. На игрока передаются
не более 128 изображений и 512 КиБ за обновление; нестандартные протоколы
создания модовых сущностей требуют отдельного адаптера.

У лодки после переноса обновляется серверная точка отсчёта проверки движения.
Отложенная коррекция восстанавливает потерянную посадку только после появления
настоящего транспорта и чанка назначения. Последующий выход из лодки отменяет
устаревшую коррекцию, чтобы она не посадила игрока обратно.

## Сохранение геометрии при переходе

`retainTransitionMeshes` включает собственный кэш готовых секций. Меши из
изображений берегов и собственных загруженных чанков перед границей компилируются штатным компилятором на одном рабочем потоке,
но хранятся по каноническим координатам. После переноса эти же GPU-буферы
рисуются в ближайшем периодическом размещении: у берега назначения и за
обратным швом для уходящей стороны. Это прикрывает подготовку реальных секций
и задержку получения новых визуальных копий уходящего берега.
После их готовности резервная геометрия пропускается, чтобы не накладывать
две поверхности. На первом холодном подходе кэш ещё может быть не готов.

Лимиты: один compile/upload job одновременно и проверка до трёх локальных
колонок за тик. Память GPU и число секций ограничены настройками
`transitionMeshMaxMiB` / `transitionMeshMaxSections`. CPU builder и накладные
расходы драйвера идут отдельно.
Кэш очищается при выходе из мира и перезагрузке ресурсов; меши покинутого берега
истекают через 200 серверных тиков. Параметр можно
выключить для сравнения с первоначальным рендером. Это первый этап сохранения
геометрии, а не готовая замена всей системе наблюдения за чанками/сущностями.

## Дальний вид через DH

При установленном **Distant Horizons 3.3.3** `dhSeamRendering` добавляет вид
противоположной стороны за пределами полосы обычных чанков. Данные остаются
в канонической базе DH: создаётся одно дополнительное дерево видимости, а
геометрия размещается со смещением на полный оборот. При переходе деревья
меняются ролями, вместо пересоздания обоих видов.

`dhPreviewDistanceBlocks` — расстояние до шва для начала подготовки дерева
(по умолчанию 512 блоков); это **не** дальность прорисовки. Дальность и качество
по-прежнему задаёт DH. Дополнительный вид использует штатные проходы DH,
включая его глубину, туман и смешивание. Готовые обычные секции и сохранённые
меши исключаются из дальнего прохода; части LOD за каноническими границами
отсекаются по пикселям, без удаления всей пересекающей границу плитки.

Цена — второе дерево видимости и его GPU-меши рядом со швом. При первом подходе,
после отключения/включения или изменения ресурсов подготовка занимает время.
Отдельный сетевой сервер DH пока не проверен; проверен одиночный мир. Шейдерпаки,
переопределённый DH terrain shader и wireframe не поддерживаются этим проходом.
Simple Clouds и перенос дальней поверхности Cruising Speed пока не интегрированы.

## Скорость и восстановление освещения (0.6.1)

Самостоятельный игрок переносится относительным vanilla-пакетом: сохраняются
его клиентская скорость полёта и предыдущая поза. Принудительный motion-пакет
с серверной скоростью игрока после такого перехода не создаётся. Перенос лодки
и авторитетная коррекция пассажира остаются отдельными от этого случая.

Свет визуальных копий хранится вместе со снимком. Только RenderChunkRegion и
клон секции Sodium используют этот источник; обычные запросы освещения уровня,
освещение сервера и спавн существ работают с настоящим light engine.
Загрузка/удаление копии больше не ставит в него задачи и не удаляет его слои.
Это устраняет небезопасное смешивание клиентских данных; происхождение уже
повреждённого серверного света в пользовательском мире отдельно не подтверждено.

Для диагностики и восстановления доступны команды с правами администратора:

```text
/around_planet lightcheck -4086 3
/around_planet relight -4086 3
```

Аргументы — **номера чанка**, а не блоки. `lightcheck` показывает реальный
серверный Sky light над центральной поверхностью и в позиции вызывающего.
`relight` асинхронно удаляет старые световые слои и пересчитывает свет загруженных
чанков в области 3×3 вокруг указанного. Незагруженные чанки пропускаются,
территория не генерируется заново и блоки не удаляются. После завершения
исправленный свет сохраняется и пересылается наблюдающим клиентам. Одновременно
допускается один такой пересчёт на измерение; команда сообщает о завершении.

## Диагностика ожидания перехода (0.6.2)

```text
/around_planet seamstatus
```

Команда администратора показывает число FULL-чанков и чанков с готовым светом
в противоположной полосе, наличие и радиус билета игрока, занятость 16 мест и
последнюю причину ожидания: `MISSING_CHUNKS` или `COLLISION`. `NO_PENDING_CROSSING`
означает отсутствие ожидающего пересечения на сервере. Переход по-прежнему
ждёт настоящей готовности назначения и не создаёт нового проникновения в блоки.
Холодная генерация может занимать время; команда не заставляет её выполняться
синхронно. Исправление 0.6.2 устраняет вытеснение запроса игрока постоянными
запросами мобов и недогрузку крайнего кольца полосы.

## Коллизии на стыке (0.6.3)

Движение, поиск опоры, проверка удушья и поиск выхода из лодки используют
периодические блоки в узкой полосе у границы. Части объёма по разные стороны
стыка проверяются по своим каноническим колонкам. Сервер читает готовые чанки,
клиент — полученные снимки; игровые чанки и освещение от этого не изменяются.
Недостающий снимок/чанк за швом временно считается препятствием; запрос коллизии
не запускает генерацию и не ждёт её синхронно.

Стена останавливает обычное движение до пересечения, сохраняя скольжение и
возможность отойти назад. Отказ из-за коллизии больше не вызывает повторные
телепортации к линии. Если объект уже пересекается с блоком, смена периодической
координаты сохраняет этот контакт: она не должна оставлять лодку с пассажиром
в служебном чанке за границей. Новое проникновение в блоки ограничивается
обычным движением. Реальные сущности назначения и vanilla border сохраняют
свою проверку. Проверка готовности пересекающего шов объёма также использует
канонические колонки и не ждёт ненужного внешнего чанка.

## Физические конструкции: отображение и рельеф (0.7.0)

Опциональный адаптер **Sable 2.0.6 / Rapier** показывает конструкцию по другую
сторону границы через штатные сетевые пакеты Sable, plot-чанки, интерполяцию и
GPU-меши. Отдельный физический двойник не создаётся. Внутри вызова рендера
выбирается ближайший периодический образ позы и AABB; логическая поза,
приватные координаты plot и серверные физические тела не меняются.
Изменения блоков и удаление конструкции обслуживает тот же native lifecycle.

Коллайдеры рельефа за швом Sable строит своим обычным методом из настоящих
секций противоположного берега. Поэтому нос конструкции может упереться в
стену за разрезом, пока центр ещё находится на исходной стороне. Учитываются
также соседи блоков на стыке; удаления и изменения стены обновляют загруженные
коллайдеры перед следующим физическим тиком. Служебные блоки за границей
не становятся источником этих коллизий. Блоки, освещение и сохранённые чанки
не копируются. Выгрузкой секций продолжает управлять менеджер Sable.

`shipSeamSupport=false` отключает адаптер; `shipSeamBandChunks=8` задаёт полосу
рельефа до 128 блоков за каждым краем (диапазон 1–32 чанка). Заказаны только
секции, нужные самой физике Sable. Для подходящих к стыку корпусов работают
не более 64 временных canonical ticket-центров с радиусом 1 и сроком 60 тиков;
они обновляются не чаще раза в 20 тиков. Подход начинается за 32 блока и
расширяется скоростью до двух секунд пути, максимум 512 блоков. В неготовом холодном участке сохраняется
обычный синхронный fallback Sable: это не гарантия отсутствия задержек генерации.
Выше build height эта дополнительная загрузка не требуется.

## Удержание геометрии после перехода (0.9.3-diagnostic)

Видимая в периодическом размещении геометрия больше не истекает через десять
секунд из-за отсутствия исходного чанка в обычном клиентском кэше. Предзахват
охватывает дальность обзора, а не только ширину полосы сетевых снимков; за тик
проверяется не более трёх колонок. Пустые результаты компиляции не скрывают LOD
и не заменяют прежнюю геометрию с теми же данными блока.

Кэш ограничен `transitionMeshMaxMiB=128` и `transitionMeshMaxSections=1536`.
При переполнении сначала вытесняются размещения вне окна обзора, затем реже
рисуемые. Секции без штатной геометрии не добавляются в локальный предзахват.
После ухода от шва невостребованные меши освобождаются как прежде.
Маска покрытия DH строится один раз за кадр для совпадающих непрозрачного и
прозрачного проходов; смена мира, секции камеры или размера маски обновляет её.

Диагностика сохранена. Если серверный тик длится более 500 мс, не чаще одного
раза в пять секунд добавляется `server.slow_tick` с коротким стеком главного
серверного потока. Это поможет отдельно разобраться с длительной генерацией DH.

## Диагностика чанков и DH (с 0.9.2-diagnostic)

По умолчанию `seamDiagnostics=true`: раз в пять секунд в `logs/latest.log`
пишутся `[AP-DIAG]` сводки клиентской/серверной загрузки, снимков, очередей мешей,
DH и политики Cruising Speed, а при переходах — отдельные метки.
`/around_planet diagmark` добавляет отметку проблемы без изменения мира.
Порядок сбора и расшифровка полей: [docs/seam-diagnostics.md](docs/seam-diagnostics.md).

## Совместимость с Fabric Biome API (0.9.1)

Сглаживание сохраняет исходный `Climate.Sampler` и его данные, включая seed
Forgified Fabric Biome API. Меняются только запросы шумов климата и компонентов
sampler'а; исходные поля record не перезаписываются. Это исправляет вылет
`fabric_getSeed: this.seed is null` при генерации чанков после входа в мир.
Новых настроек и изменений сохранений для исправления не требуется.

## Сглаживание генерации (0.9.0)

`terrainSeamBlending=true` включает сглаживание новой шумовой генерации Overworld.
`terrainBlendWidthBlocks=256` задаёт ширину полосы **на каждом берегу**; допустимо
32–2048 блоков, фактическое значение ограничено четвертью окружности мира.
При `boundaryX=256` полоса поэтому составит не более 128 блоков на берег.
Настройки читаются при открытии мира: после их изменения нужен перезапуск.

Генератор плавно смешивает значения шумов с двух краёв кривой пятой степени.
На линии шва плотность рельефа и климат согласованы, а к внутреннему краю полосы
влияние плавно сходит к нулю. Штатные сплайны, интерполяция, кэши клеток и построение
поверхности продолжают работать поверх этих значений. Далеко от шва дополнительных
вычислений шумов нет; в полосе добавляются выборки, но не генерация/загрузка
противоположных чанков. Параметры принадлежат конкретному состоянию генератора,
без глобальной подмены координат, seed или настроек других измерений.

**Сохранённые чанки не переписываются.** Для проверки используйте новый мир либо
ещё не сгенерированный участок границы. Стык старой и новой генерации не является
миграцией и отдельно не сглаживается. Отключение настройки возвращает исходную
генерацию только для будущих чанков; смена ширины или `boundaryX` тоже меняет её.

Это первый этап: согласуются базовый рельеф, входные шумы пещер/аквиферов и климат
для выбора биома. Самостоятельные карверы, размещение деревьев/структур, локальная
случайность аквиферов и деталей поверхности ещё могут различаться у шва. Чужой
генератор с собственной реализацией шумов требует отдельной интеграции. Плоские
миры, Nether и End не изменяются. Simple Clouds не затрагивается; пользователь
подтвердил его совместную работу с независимым рендером в 0.8.1.

## Освещение сущностей и ломание блоков (0.8.1)

Изображения сущностей используют свет снимка противоположного берега в точке
освещения модели. Это касается и небесного света, и света от блоков; собственное
свечение рендерера и яркость горящих сущностей сохраняются. Настоящие сущности и
игровой light engine от этого не меняются.

Проверки блока в обработчиках первого и удерживаемого нажатия атаки теперь тоже
читают снимки. Поэтому ломание через границу доходит до штатного игрового
контроллера и серверной проверки, включая постепенное добывание в выживании.
Раньше эти проверки видели воздух и могли вообще не отправлять запрос ломания.

## Перенос конструкций и действия с берегом (0.8.0)

`shipSeamTransfers=true` переносит группу жёстко связанных тел Sable, когда
её **общий центр масс** пересекает линию. Каждый собственный mass tracker
учитывается ровно один раз; дочерний swivel-подуровень не переходит отдельно.
Все тела получают одно смещение по X. Их UUID, plot, ориентация, линейная и
угловая скорости и локальные точки шарниров сохраняются. Стоящие сущности и
транспорт с пассажирами перемещаются вместе с группой. Если участок назначения
ещё не FULL, перенос откладывается без синхронной генерации из его обработчика.
Обычный холодный fallback физики Sable при подготовке коллайдеров остаётся.

Клиент получает надёжное сообщение смены координат перед пакетами пассажиров.
Оно сдвигает историю поз, снимки интерполяции и bounds, сохраняя сам объект и
GPU-меш. Поздний снимок UDP со старой стороны приводится к новой системе
координат; интерполяция не проводится через весь мир. Настоящие игроки без
нового сетевого канала не переносятся частично отдельно от группы: обновите
мод на сервере и всех клиентах.

Игрок может ходить по выступающей за линию части палубы до перехода центра.
При этом работают наведение, ломание в обычном/творческом режиме, установка,
использование блоков и меню противоположного берега, а также обычное ведро.
Запросы переводятся в канонические позиции и проходят штатные packet handlers,
game mode, дальность, ограничения режима приключения и события NeoForge.
Нормализуются и соседние позиции размещения на самом шве. Позиция игрока ради
взаимодействия не подменяется. Клиент читает снимки только внутри наведения и
действий, не пишет предсказанные блоки в игровые чанки и получает авторитетные
обновления изображения с сервера.

Полоса снимков следует за игроком на длинном носу; он не ограничен первыми
четырьмя колонками у линии. В проверке используется палуба длиной 177 блоков и
игрок в 76 блоках за швом, пока центр конструкции остаётся перед ним.
`shipSeamTransfers=false` сохраняет отображение и коллизии 0.7.0 без переноса.
Для длинных корпусов согласуйте `shipSeamBandChunks` (полоса коллайдеров) и
`guardMarginBlocks` (запас border); увеличение одного не меняет другое.

## Что ещё не реализовано

Это пока не полностью бесшовная планета. Клиентские снимки дополнительно
используются для предсказания коллизий и действий с блоками у шва.
Физические столкновения двух конструкций, атаки/подбор сущностей через разрез
и согласование размещения структур/карверов пока не реализованы. При переходе обычная область клиента всё ещё меняется. Кэш прикрывает
готовыми мешами задержку её компиляции, но не гарантирует отсутствие подгрузки
на холодном кэше, при пересылке сущностей или специальных block entity. При резком перепаде высот обратный переход по-прежнему может
блокироваться реальными блоками назначения.

Обычный транспорт переносится вместе с пассажирами без их отсоединения.
Пассажиры Sable исключены из независимого переноса обычных сущностей — ими
управляет перенос несущей группы. Привязанные к миру, неизвестным кинематическим
телам или тросам группы пока не переносятся: перенос частиц троса и внешних
связей требует отдельного согласования. Лимит одной группы — 256 подуровней.
Внешний поводок блокирует перенос группы; если оба его конца перемещаются
вместе, связь сохраняется. Удалённый multiplayer
и произвольные обработчики взаимодействий сторонних модов требуют проверки
в конкретной сборке.

Cruising Speed остаётся отдельным модом `cruising`. Его код, конфиги и рендеринг
не копируются в around_planet. Текущее совместное использование ещё не исправляет
скачок измеренной скорости камеры в Cruising Speed при телепортации. Будущие
стыковки описаны в [docs/architecture.md](docs/architecture.md).

## Разработка и проверки

```sh
bash ./gradlew build
bash ./gradlew -PplanetTests runGameTestServer
bash ./gradlew runClient
```

JAR: `build/libs/around_planet-0.10.1.jar`.
`-PcompatModsDir=/absolute/path/to/test-mods` добавляет локальные JAR только в
среду запуска; они не включаются в мод. Серверные и клиентские тестовые классы
также не входят в итоговый JAR. Клиентский smoke-тест запускается с
`-PplanetClientSmoke runClient` и требует отдельного подготовленного мира
`run/saves/around-ew-smoke` с включённым переходом и `boundaryX = 256`.
Для графической проверки добавьте `-PplanetVisualSmoke`: проверяются настоящий
GPU-рендер обоих берегов, вода, обновления блоков, изоляция от игрового кэша и
фильтры DH при его наличии.

`-PplanetEntitySmoke` вместо `-PplanetVisualSmoke` проверяет модели сущностей
через настоящий сетевой канал и GPU, движение, экипировку, пассажиров, удаление
и очистку. Затем выполняется регрессия лодки: потерянная посадка, гребля через
обе границы, продолжение движения и выход по Shift. Все эти проверки изменяют
только отдельный подготовленный тестовый мир.

Разбор предоставленных JAR Immersive Portals и план устранения перезагрузки:
[docs/immersive-portals-analysis.md](docs/immersive-portals-analysis.md).

Для проверки коллизий добавьте `-PplanetCollisionSmoke` к клиентскому smoke-запуску:
реальный ввод проверяет остановку у стены, проход высотой два блока в обе стороны
при несовпадающих служебных блоках и выход по Shift из застрявшей лодки.

`-PplanetShipSmoke` проверяет настоящий Sable-рендер конструкций через оба края,
обновление блоков в том же GPU-меше, изоляцию логической позы и штатное удаление.
Для него нужен Sable 2.0.6 в `compatModsDir`; тестовый мир тот же, `boundaryX=256`.
Серверный `-PplanetTests` с Sable дополнительно проверяет настоящий контакт
физического тела со стеной противоположного берега и движение после её удаления.

`-PplanetShipTransferSmoke` проверяет настоящего игрока на выступающей палубе:
луч наведения, использование/ломание/установку, сундук, переход несущей конструкции
в обе стороны с сохранением локальной точки и GPU-меша, поздние снимки старой
стороны. Применяется к тому же отдельному тестовому миру с `boundaryX=256`.

Эксперимент прогрессивной генерации DH: [настройки и принцип работы](docs/dh-progressive.md).
В `dhProgressive` можно отключить эксперимент для сравнения. Грубые ячейки
8 блоков последовательно уточняются до 4, 2 и 1 через штатный провайдер DH.

С Cruising 1.1.0+ прогрессивной генерацией управляет Cruising. Around Planet
не запускает вторую очередь, даже если эксперимент включён в старом конфиге мира.
Без новой версии Cruising прежний эксперимент остаётся доступен.
