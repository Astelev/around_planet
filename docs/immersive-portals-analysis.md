# Что полезно из Immersive Portals для around_planet

Проверены метаданные и декомпилированы выбранные классы двух предоставленных JAR:
`immersive-portals-5.2.0-mc1.20.1-fabric.jar` и
`immersive_portals-6.0.7-all.jar`. NeoForge-версия дополнительно проверена запуском
с нашими тестовыми модами. В production-зависимости она не добавлена из-за
воспроизведённых конфликтов ниже. Fabric-версия использовалась только для анализа.

## Результат проверки зависимости

Совпадение Minecraft/NeoForge не обеспечивает совместимость с остальными модами.
Для предоставленной версии 6.0.7 воспроизведены два независимых сбоя:

| Проверка | Результат |
| --- | --- |
| IP + Sable 2.0.6 + Sodium 0.8.13 + DH 3.3.3 + Cruising Speed | Сбой при применении `sable.mixins.json:player_standup.PlayerMixin`: IP `MixinPlayer_Collision` заменил `Player.canPlayerFitWithinBlocksAndEntitiesWhen(Pose)`, куда Sable добавляет проверку коллизии с конструкциями |
| IP + Sodium 0.8.13 + DH + Cruising Speed, без Sable, с Cloth Config 15.0.140 | После загрузки модов и прохождения информационных экранов — сбой при создании мира: `MixinSodiumOcclusionCuller` ожидает отсутствующий `OcclusionCuller$Visitor` |

Без Cloth Config второй запуск сначала останавливался ещё раньше на
`NoClassDefFoundError: me/shedaniel/autoconfig/ConfigData`. Внешний Cloth Config
добавлен в тестовую среду; его установка не исправляет два конфликта выше.
Архив `-all.jar` не содержит этой библиотеки и не объявляет её в проверенном TOML.

Следовательно, сделать этот JAR обязательной зависимостью текущей проверяемой
комбинации пока нельзя. Для backend на его основе сначала нужны совместимая
реализация коллизий IP/Sable и обновлённый адаптер Sodium. Простое выключение
проверки Sable затрагивает контакт игрока с кораблём и не является проверенным
исправлением. Перенос физических кораблей останется отдельной интеграцией даже
после исправления запуска. Другие версии этих модов здесь не испытывались.

## Подходящая версия и библиотеки

Вторая версия объявляет Minecraft `[1.21.1,1.21.2)` и NeoForge `[21.1,)` — наша
базовая платформа подходит. В одном JAR находятся `immersive_portals_core`,
`q_misc_util` и `imm_ptl`. Источник форка:
[iPortalTeam/ImmersivePortalsModForNeo](https://github.com/iPortalTeam/ImmersivePortalsModForNeo).
Метаданные объявляют Apache-2.0. Исходный код и бинарники в around_planet не копировались.

| Компонент | Что даёт | Применимость |
| --- | --- | --- |
| Ядро Immersive Portals | Кэш миров/чанков, трекинг, преобразования, рендер, телепортация | Полная система с большим числом mixin; возможный отдельный backend требует испытаний с DH, Sable и конкретным Sodium |
| QMiscUtil | Задачи, сигналы, вспомогательный RPC и данные измерений | Не самостоятельная библиотека бесшовного рендера; наши NeoForge-события и payload уже покрывают часть этих функций |
| Mixin/MixinExtras | Перехват функций игры | Этот механизм уже есть в нашей среде; старая Fabric-версия библиотеки из первого JAR не нужна |
| Cloth Config / AutoConfig | Экран и данные настроек | Fabric JAR включает библиотеку; NeoForge JAR требует её снаружи. Не отвечает за порталы или сохранение геометрии |

В NeoForge JAR нет вложенных JAR зависимостей. Интеграции Sodium/Iris находятся
в самом ядре и включаются mixin-плагином. Проверенный адаптер несовместим
с Sodium 0.8.13. Например, `SodiumInterface` обращается
к контексту `RenderSectionManager`; версия полей и жизненный цикл здесь существенны.

## Как устроен переход

1. `ClientWorldLoader` хранит `ClientLevel`, `LevelRenderer` и вспомогательное
   состояние по измерению. Удалённый мир существует заранее. Для перехода внутри
   одного измерения источник и назначение используют один канонический мир;
   отдельное измерение для каждого вида через портал не требуется.
2. `ImmPtlClientChunkMap` заменяет ограниченный центром обзора кэш на разреженные
   карты чанков. Дальняя область не исчезает только потому, что изменился центр.
   Чанки выгружаются явно; чтение с потоков компиляции согласовано с изменениями
   карты на основном потоке. Это важнее, чем просто увеличить view distance.
3. `PacketRedirection` / `PacketRedirectionClient` оборачивают обычные пакеты
   указанием измерения и применяют их в нужном клиентском контексте на основном
   потоке. `EntitySync` расширяет обычный трекинг и отправку изменений сущностей.
   Обновление внешнего вида не требует пересылки полного NBT на каждом шаге.
4. `ImmPtlChunkTracking` хранит наблюдение чанков игроками и расстояние до источника
   загрузки. `PlayerChunkLoading` отправляет ближние группы раньше дальних,
   учитывает квоту и подтверждения пакетов `ChunkBatch`; клиент сообщает желаемый
   темп загрузки. Локальное соединение имеет отдельный режим. Фиксированное число
   пакетов само по себе не учитывает скорость клиентской компиляции.
5. Рендер строит вид с преобразованной камерой и ограничивает изображение
   поверхностью портала. `CrossPortalEntityRenderer` отдельно обрабатывает
   проекции и отсечение пересекающих портал сущностей. `SodiumRenderingContext`
   и соответствующие mixin переключают списки рендера/контекст видимости.
6. `ClientTeleportationManager` преобразует текущую и предыдущую позицию глаз,
   скорость, поворот и транспорт на клиенте, затем сообщает о переходе серверу.
   `ServerTeleportationManager` проверяет допустимость и согласует серверное
   состояние. Обычная телепортация с ожиданием перезагрузки — другой путь.
7. `WorldWrappingPortal.initWrappingPortal` уже создаёт переход между
   противоположными поверхностями области в том же измерении. Это прямой пример
   нужной нам западной/восточной топологии, хотя не готовый адаптер к нашим модам.

`SharedBlockMeshBuffers` не является универсальным решением для Sodium:
в Fabric 5.2.0 его режим выключен при наличии Sodium, а в NeoForge 6.0.7 этот
класс уже помечен deprecated и содержит только пустой `init`. Подключение этого
класса само по себе не уменьшит наши затраты.

## Что менять у нас следующими итерациями

Полная перезагрузка при пересечении шва не является принципиальным ограничением.
Сейчас у нас есть канонические серверные чанки и отдельные снимки по координатам
изображения. После перехода обычному кэшу и компилятору приходится получать и
собирать эту территорию снова. Сохранить только блоки недостаточно: для устранения
мигания нужны также готовая геометрия, свет, видимость и согласованная камера.

1. **Один канонический кэш данных.** Хранить подписки на обе береговые области.
   Вид за границей ссылается на исходный чанк и преобразование X; сохранённые
   координаты `LevelChunk` и физический мир не переписывать. Ключ наблюдения:
   измерение + исходный `ChunkPos`, ключ размещения вида — ещё и преобразование.
2. **Переиспользование готовых секций.** Сохранить контекст Sodium/vanilla и
   размещать исходную геометрию со сдвигом камеры. Проверить границы render regions,
   прозрачные слои, frustum/occlusion, свет и несколько размещений одной секции.
   Перестановка ссылок на `LevelChunk` без этих изменений ещё оставит видимый провал.
3. **Наблюдение и дельты.** Вместо полных кадров metadata 5 раз в секунду отправлять
   создание/изменение/удаление по подпискам обычного трекера; готовность чанка должна
   предшествовать его сущностям. Ввести измеряемую очередь и квоту с подтверждением
   готовности клиента, не копировать большие лимиты локального соединения.
4. **Единый переход.** Согласовать игрока, корневой транспорт и пассажиров по одной
   последовательности переходов; преобразовать обе позиции интерполяции камеры.
   Сохранить серверную проверку координат, коллизий и законности перехода. Не
   отключать обычные проверки движения глобально ради исчезновения рывка.
5. **Совместимость.** Приватные координаты Sable остаются отдельными от географии;
   перенос физического корабля выполняется его API. DH и Cruising Speed используют
   то же преобразование вида, но не должны записывать изображения как новые
   исходные чанки. Север/юг с поворотом добавляется после проверенной EW-версии.

Перед заменой текущего пути нужны прогоны с удалённым клиентом и задержкой сети,
повторными переходами, пассажирами, обновлениями блоков, светом и очисткой ресурсов.
Отдельно сравниваются число пересборок секций, время кадра, байты сети и память.
Более сложная архитектура не гарантирует меньший расход ресурсов без измерений.
