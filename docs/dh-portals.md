# DH 3.3.3 и EW-шов: 0.4.5

Штатный DH через `AbstractImmersivePortalsAccessor.BeforeRenderEvent` отменяет
отрисовку внутри порталов. Кроме того, один `ClientRenderState` перемещает центр
quadtree при переходе на противоположную границу, закрывая старые render sections.
Это отдельные причины отсутствия дальнего вида и потери готовых LOD при переходе.

## Данные и жизненный цикл

`DhPortalViews` привязан к `ClientLevelModule`. В полосе `dhPreviewDistanceBlocks`
(по умолчанию 512) он создаёт второе дерево из того же `IDhClientLevel` и
`fullDataSourceProvider`. Новые миры, базы данных и полные Minecraft-чанки
для этого не создаются. Дополнительный объём равен одному render tree DH с его
текущей дистанцией; это увеличивает потребление памяти и фоновую работу у шва.

Положение берётся из сохранённого IP исходного player position, чтобы временная
смена камеры в portal render не перескакивала между центрами. Второе дерево
тикает у преобразованной позиции. При скачке X на один оборот и наличии
подготовленного дерева оно становится `ClientRenderStateRef` до штатного тика DH.
Прежнее дерево остаётся для возврата. Это сохранение готового набора, а не
гарантия, что при дальнейшем движении DH вообще не обновит ни одной секции.

Оба набора получают уведомления `OnDataSourceUpdated`/`reloadPos`.
Второй закрывается при уходе от шва, остановке рендера, reload/config changes
и закрытии уровня. `dhPortalRendering=false` отключает предзагрузку и допуск
портального DH-прохода. Чужие порталы, рекурсия и Iris shader packs сохраняют
штатную отмену DH.

## Рендер

`RenderParams` для первого уровня нашего параллельного EW-портала получает
противоположный buffer handler и преобразованную точную камеру. Только после
такого выбора разрешается пройти штатный cancel-event DH.

Обычный `LodRenderer` внутри портала заменён прямым terrain pass в текущий
stencil target IP. Стандартный DH fullscreen composite при первом эксперименте
перекрывал живые чанки, поэтому здесь не используются его FBO/fog/SSAO/AA.
Перед draw строится render list с дальним frustum DH; для записи глубины shader
получает Minecraft projection текущего портального вида. Depth clamp сохраняет
дальние примитивы за vanilla far plane. Stencil и текущий framebuffer сохраняются;
GL state, depth clamp, clip-distance enable и ссылка на текущую DH-программу
восстанавливаются после draw. Штатный основной DH-проход не заменяется.

В 0.4.5 render list строится по исходной projection камеры с ближней плоскостью
0.05 и дальностью DH. Так overdraw near plane и портальная oblique projection
не отбрасывают секции у шва. После штатного fillUniformData только в нашем
проходе `uClipDistance` сбрасывается в 0 и выключается ближний dither: исходный
форк оставлял здесь +16 блоков даже после своей near-clip правки.

Depth clamp отключает как дальнее, так и обычное ближнее отсечение. Вершинный
шейдер теперь явно пишет `gl_ClipDistance[0] = gl_Position.w - 0.05` в нашем
проходе. Это отсекает геометрию у eye plane, сохраняя дальние примитивы; вне
нашего прохода uniform отключён. Основные настройки overdraw DH не меняются.

## Настоящие чанки

С 0.4.5 `chunkPreloadDistanceBlocks` задаёт полосу начала загрузки настоящих
чанков (по умолчанию 512). Радиус плавно растёт от 2 до меньшего из `chunkRadius`
(по умолчанию 16) и обычной view distance игрока. Телепортация и контракты
ChunkLoader остаются прежними. Центр загрузчика переносится внутрь канонического
края назначения: EAST загружает от чанка -4096, WEST — от 4095 при boundaryX=65536.
Иначе виртуальная камера центрирует область снаружи канонического мира, и source
mask отбрасывает большую часть ранней загрузки. Вне полосы управляемые
порталы не добавляются в nearby loading list. Чужие порталы не меняются.
Это заранее распределяет рост области вместо штатного сжатия радиуса на один
чанк за каждые 16 блоков расстояния до плоскости. Большие значения всё ещё
требуют больше генерации, памяти и трафика; это не обещание отсутствия пауз.

## Перекрытие портала глубиной основного LOD

Финальный DH `copy/gl/apply.frag` выводит только цвет и не пишет `gl_FragDepth`.
Stencil-движок IP рисует порталы в `onBeforeTranslucentRendering`, после
непрозрачного рельефа. Поэтому основной LOD мог быть виден по цвету, но не
защищать ближний рельеф от более далёкой плоскости портала.

`DhPortalDepth` захватывает основной RenderParams и перед stencil-порталами
перерисовывает готовые opaque VBO только в глубину MC target. Используется
проекция Minecraft, совпадающая с плоскостью портала; исходные DH uniform matrix,
GL state и color mask восстанавливаются. Цвет не меняется, генератор и quadtree
повторно не запускаются. Проход выполняется только после выбора видимого
управляемого портала; пустые/transparent-only списки пропускаются. Проход
ограничен областью видимости шва, главным видом и штатным OpenGL-шейдером DH;
не подменяет чужие shader overrides или Iris. Кэш последнего кадра сбрасывается
при закрытии DH-уровня. Прозрачная вода в этот opaque-depth проход не входит.

GPU-регрессия воспроизводит ошибку: цвет рельефа без глубины перекрывает дальний
синий «портал». С production depthOnly-контекстом ближний красный рельеф остаётся,
а портал перед ним по-прежнему виден. Клиентский harness также ждёт фактических
opaque draw calls основного DH, затем повторяет GPU-отсечение, наклонный ракурс,
сохранение деревьев при переходах и лодку. Это не pixel-perfect воспроизведение
пользовательского мира; прозрачная вода/туман остаются отдельными ограничениями.

Следствие: в портале пока нет тех же fog/SSAO/AA, что в основном виде. Видимость
и стык воды/тумана могут отличаться. Simple Clouds не исправлен этим адаптером.

## Отсечение у плоскости

Старая маска `getRenderingEnabled` отбрасывала целиком любую DH-секцию,
не помещавшуюся в канонический диапазон. Новая отбрасывает только полностью
внешние секции. В terrain fragment shader добавлена проверка X каждого
фрагмента; границы передаются относительно точной камеры, как `vertexWorldPos`
самого DH. Поэтому пересекающая шов секция сохраняет внутреннюю часть, не
показывая внешний рельеф. Генерационная маска DH остаётся канонической.

## Проверено

Клиентский harness с Sable 2.0.6, Sodium 0.8.13, Create 6.0.10, Veil 4.3.2,
DH 3.3.3 и Cruising 1.0.0 ждёт не пустое дерево, а uploaded GPU-буферы в portal
render list. Сохраняется проверка GPU-пикселя настоящего
противоположного берега. После восточного перехода primary совпадает с прежним
opposite по идентичности объекта, после западного — с исходным primary. Проходят
проверки удалённого моба, столкновений Sable, обоих переходов на Y=640 и лодки.
Отдельный offscreen GPU-тест компилирует настоящий изменённый DH fragment shader
и рисует пересекающий обе плоскости примитив: пиксель внутри сохраняется, оба
внешних пикселя отбрасываются. Клиентский прогон без установленного DH также
проходит, включая Sable, рендер чанков, оба перехода и лодку.

Не проверены полный пользовательский набор модов, Iris, рекурсивные порталы,
максимальные скорости и pixel-perfect совпадение с пользовательским скриншотом.
DH остаётся необязательным: Maven-артефакт используется только как compile API.
