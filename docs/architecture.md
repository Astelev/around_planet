# Архитектура around_planet 0.4

## Владение состоянием

around_planet — мод интеграции с Immersive Aeronautics 1.1.4, а не второй
портальный движок. Обычные данные мира, сущности, сетевые обновления, кэш,
рендер прохода, взаимодействия и телепортацию ведёт зависимость. Старые
`TransferService`, снимки чанков/сущностей, их payload и render-region подмены
удалены. Vanilla border не переписывается.

`PortalLayout` описывает две параллельные плоскости X, их высоту и охват Z.
`PlanetPortals` на старте сервера согласует пару с конфигурацией. Теги порталов
служат признаком владения. При совпадающей геометрии объекты сохраняются;
дубликаты/устаревшая геометрия заменяются, при отключении удаляются только наши
теги. Чужие записи `GlobalPortalStorage` остаются на месте.

Это отдельные глобальные `Portal`, а не `WorldWrappingPortal.WrappingZone`,
валидность которой требует четырёх сторон. Пара сохраняется и синхронизируется
самим Aeronautics. `PlanetBorders` теперь только индексирует неизменяемую
топологию по объекту border для интеграций; не меняет его геометрию.

## Подписки и внешние данные

`PortalChunkWatchMixin` ограничивает создание player-watch записей в
`ImmPtlChunkTracking.updateForPlayer`. Колонки канонического интервала и одна
внешняя колонка с каждой стороны разрешены. Приватная область Sable разрешена
отдельно; при неизвестном API её защита действует в сторону сохранения кораблей.

Общий `ChunkLoader.foreachChunkPos`, его `getChunkNum`/`isFullyLoaded`, генератор,
игровой chunk cache и отдельные forced tickets не изменяются. Это сохраняет
контракт ожидания загрузки и служебные зависимости движка.

`PortalMobDistance` и узкий `Mob.checkDespawn` mixin учитывают короткую дистанцию
через управляемый шов внутри его высот/Z. Это необходимо и при начальной загрузке,
до завершения сетевого наблюдения. Peaceful, persistence и NeoForge-проверки
остаются штатными; координаты игроков, навигация и прочие функции расстояния
не подменяются.

Для DH 3.3.3 внешний рельеф отсекается по плоскости в terrain fragment shader.
Полностью внешние секции не рисуются; частичные сохраняются, чтобы не оставлять
полосу шириной в крупную секцию. Второе дерево `ClientRenderState` использует
тот же канонический data provider. При пересечении X-шва деревья меняются ролями
до штатного tick/recenter, сохраняя готовые GPU-буферы. Обновления данных приходят
в оба дерева; второе закрывается вдали от шва, при изменении настроек и выходе.
См. [dh-portals.md](dh-portals.md) для прохода геометрии и ограничений.
Cruising Speed получает маску внешних колонок; его портальный проход и история
скорости камеры требуют следующей итерации.

## Защита кораблей и исправления зависимости

Форк умеет переносить Sable через обычные порталы, но его корабельный поиск не
включает `GlobalPortalStorage`. `ManagedPortalPassengerMixin` запрещает только
нашим порталам переносить отслеживаемого Sable пассажира отдельно от корпуса.
Поведение чужих обычных порталов форка не меняется.

В предоставленном форке `GlobalPortalStorage.init` регистрирует `onServerClose`
на `ServerTickEvent.Post`. Это воспроизведено GameTest: после десяти тиков новые
глобальные порталы уже помечены removed. `GlobalPortalStorageTickMixin` отменяет
такое закрытие, пока сервер работает. Штатное завершение при остановленном сервере
не блокируется. JAR зависимости не перепаковывается.

Create объявлен обязательным из-за фактической ссылки без проверки на
`CarriageContraptionEntity` в client train-rider hook форка: она вызывается даже
для лодки. Cloth Config нужен его AutoConfig. Простого совпадения внутренней
версии 6.0.7 недостаточно — проверяется маркер корабельного модуля Aeronautics.

## Проверки и границы результата

14 изолированных математических тестов покрывают периодичность и X/LOD-границы,
включая частичные секции на границе, не кратной ширине LOD-секции, а также
монотонное расширение радиуса загрузки, ограничения view distance/config и
привязку загрузки к каноническим чанкам противоположного края.
Нативный GameTest проверяет геометрию API, высоту, идемпотентность пары, замену
конфигурации, отключение, сохранение чужих порталов, политику подписок и жизненный
цикл глобальных порталов.

Клиентский harness проверяет настоящие GPU-пиксели другой стороны и получение
моба в обычном `ClientLevel`, движение игрока через обе плоскости на Y=640,
сохранение `ClientLevel`, `LevelRenderer` и ссылки на заранее загруженный чанк,
затем реальную греблю и выход по Shift. Удалённый клиент, физический корабль,
шейдерпаки и максимальные скорости пока не испытывались.

Следующие этапы: глобальные порталы в корабельном поиске и same-dimension sync,
перенос корпуса/пассажиров без пересоздания и потери скорости, затем сквозные
Cruising-виды, дополнительные эффекты DH в портале и северная/южная топология. Сначала измеряются пересборки, память,
сеть и поведение при задержке сервера, а не предполагается нулевая стоимость.
